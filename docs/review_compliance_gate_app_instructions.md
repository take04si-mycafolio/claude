# 【アプリ側実装指示】口コミ承認制＋薬機法ゲート対応

sc-tsusho の Django バックエンド(https://sc-tsusho.jp/api/)で、2026-07-30 に口コミ投稿の仕様が2点変わった。サーバ側は実装・本番反映済み。このアプリ(iPhoneアプリ)側の対応を実装してほしい。

対象は既存実装済みの投稿系エンドポイント:

- `POST /api/reviews/`(口コミ投稿)
- `POST /api/products/{id}/use-logs/`(使用記録投稿 — アプリに実装済みの場合)

認証(JWT)・リクエスト形式・成功時のステータス(201)は従来と変わらない。

---

## 変更点1: 投稿は承認制になった

- 投稿成功(201)のレスポンスで `is_approved` が常に `false` で返るようになった(以前は即承認で `true`)。
- 運営が管理画面で内容確認・承認すると商品ページに掲載される。
- `GET /api/products/{id}/reviews/` は従来どおり承認済みのみ返す。つまり**投稿直後の自分の口コミは商品ページの一覧に出ない**。
- `GET /api/reviews/my/` には承認待ちも含まれ、各項目の `is_approved` で判別できる。

### 実装すること
1. 投稿成功時の完了メッセージを変更:「投稿ありがとうございます。内容を確認のうえ掲載されます。」のような、即掲載ではない文言にする。
2. マイページの自分の投稿一覧で、`is_approved: false` の口コミに「確認中」バッジを表示する。
3. 投稿直後に商品ページの口コミ一覧を再取得して「自分の投稿が出ない」ことを不具合扱いしているロジックがあれば直す(楽観的に一覧へ差し込む実装をしている場合は削除)。

## 変更点2: 投稿時に薬機法・景表法ゲートが入った

タイトル・本文に掲載できない表現(効果の断定・「治る」「最強」「絶対」など)が含まれると、投稿APIが **400** で構造化された指摘を返す。

従来の 400(重複投稿・バリデーションエラー)と同じく `detail` を持つが、**`compliance` オブジェクトが付いているのがゲート判定の目印**。`compliance` キーの有無で分岐すること。

### 400 レスポンス例

```json
{
  "detail": "掲載できない表現が含まれています。指摘箇所を修正して再投稿してください。",
  "compliance": {
    "hint": "「私の場合は〜でした」「〜な気がします」のように、あくまで個人の感想として書いていただくと掲載しやすくなります。",
    "findings": [
      {
        "field": "body",
        "severity": "CRITICAL",
        "headline": "体への効果・変化を断定する表現は、薬機法の関係で掲載できません",
        "match": "シミが消え",
        "start": 12,
        "end": 17,
        "reason": "シミ・シワ・たるみが「消える・治る」といった断定は書けません。",
        "example": "肌が明るく見えるようになった気がします / メイクのりが良くなりました"
      }
    ],
    "suggested_title": null,
    "suggested_body": "…(全文の言い換え案。作れない場合は null)…"
  }
}
```

### フィールドの意味

| キー | 説明 |
|---|---|
| `hint` | 書き方の全体ヒント。指摘リストの上に常時表示する |
| `findings[].field` | `"title"` / `"body"` のどちらで検出されたか |
| `findings[].severity` | `CRITICAL` / `HIGH` / `KEIHYO` / `SAFETY`(表示上は区別不要。将来の並び替え用) |
| `findings[].headline` | カテゴリ見出し。そのままユーザーに見せられる平易な文 |
| `findings[].match` | 検出された文字列そのもの |
| `findings[].start` / `end` | 該当フィールド内の文字位置(0始まり、`text[start:end] == match`)。入力欄ハイライト用 |
| `findings[].reason` | なぜ掲載できないかの説明(表示用) |
| `findings[].example` | 言い換え例(表示用) |
| `suggested_title` / `suggested_body` | 全該当箇所を機械置換できた場合のみ入る言い換え済み全文。作れない場合は `null` |

`findings` は出現位置順にソート済み。同じ箇所に複数件返ることは基本ないが、重複表示に耐える実装にしておく。

### 実装すること
1. **レスポンスモデル追加**: `compliance` ペイロードをデコードする型(例: `ComplianceError` / `ComplianceFinding`)を API クライアント層に追加。400 のボディに `compliance` があればこの型として投稿画面へ返す。
2. **指摘UI**: 投稿失敗時に `compliance` があれば専用のシート(またはインライン表示)を出す:
   - 最上部に `hint` を常時表示。
   - `findings` を1件ずつカードで列挙:「タイトル/本文」の別・該当表現(`match`)・`reason`・言い換え例(`example`)。`headline` は同一カテゴリが続く場合セクション見出しとして1回だけ表示でよい。
   - 入力欄の該当箇所ハイライトは任意(できれば)。`start`/`end` は **Unicode コードポイント(Swift の `unicodeScalars`)基準のオフセット**。Swift の `String.Index`(書記素クラスタ)とはズレ得るので、絵文字入り本文でも壊れないよう `unicodeScalars` 経由で変換するか、`match` 文字列の検索で位置決めすること。
   - `suggested_body`(`suggested_title` も同様)が非 null なら「この言い換えを反映する」ボタンを表示し、タップで入力欄を置き換える。**自動再送信はしない**(ユーザーが確認・編集してから再投稿)。
3. **入力は破棄しない**: 400 になっても入力中のタイトル・本文・写真・評価はフォームに残す。
4. **使用記録投稿にも同一対応**: `POST /api/products/{id}/use-logs/` も同じルール・同じレスポンス形式でゲートされる。指摘UIとデコード処理は共通化する。
5. **既存の 400 処理は維持**: `compliance` が無い 400(重複投稿「この商品にはすでに口コミを投稿済みです。」等)は従来どおり `detail` を表示する。

## 動作確認

ステージング/本番 API に対し、本文に「シミが消えた」を含めて投稿すると 400 + `compliance` が返る(CRITICAL)。「絶対おすすめ」なら `suggested_body` に「とてもおすすめ」への置換文が入るケースを確認できる。正常文(「肌がしっとりした気がします」等)は 201 で `is_approved: false`。

確認観点:
- [ ] NG文で 400 → 指摘シートが出て、hint・該当表現・理由・例文が読める
- [ ] `suggested_body` があるケースで「言い換えを反映」→ 入力欄が置き換わり、再投稿で 201
- [ ] `suggested_body: null` のケースでボタンが出ない
- [ ] 400 後も入力内容・添付写真が消えない
- [ ] 201 後の完了文言が「確認のうえ掲載」になっている
- [ ] マイページで承認待ち口コミに「確認中」バッジ
- [ ] 重複投稿の 400(compliance無し)が従来どおり表示される
- [ ] 使用記録投稿でも同じ指摘UIが動く
